# Pure Harness 완성 설계 — 사용자 검토안 (2026-10-08)

## 목적과 완료의 뜻

처음 쓰는 사람이 별도 Harness 설치와 제품 프로젝트 하나를 선택해, 새 프로젝트 시작 또는 기존 프로젝트의 비파괴 연결을 끝내고, 실제 AI 도구에서 역할·Skill·훅 및 대시보드가 작동하는지 확인할 수 있게 한다. 이미 완성된 것처럼 보이는 후보 생성이나 화면만으로 완료를 선언하지 않는다. 이 문서는 **설계 승인용**이며 아직 구현 계획이나 설치 승인, 원본 프로젝트 정리 승인이 아니다. 실제 관찰과 통과/미확인 기준은 [완료 확인표](../../pure-harness-completion-checklist.md)에 둔다.

사용자가 승인한 기본 방향은 **범용 엔진 + 최소 프로젝트 브리지**다. 기본 사용은 Harness 하나와 프로젝트 하나이며 다중 프로젝트는 선택 기능이다. 엔진 소스와 제품 checkout은 서로 포함하지 않는 별도 루트다. `projects/<id>/`에는 Harness 관리 데이터만 놓고 제품 코드를 복제하지 않는다. 원본 엔진에 특정 제품 이름·문구·정책·코어 경로를 넣지 않는다.

## 현재 기준과 결손

구현 기준 커밋은 `05c1ba4`다. 명시적 프로젝트 컨텍스트 검증, 선택 프로젝트 runtime, 대시보드, 수동 Codex rollout 가져오기와 프라이버시 제한, 네 대상 후보 내보내기와 **일회용 checkout 시험 설치**는 있다. 이것은 새/기존 프로젝트의 실제 안전한 연결이나 네이티브 동작 검증과 다르다. 지금은 manifest와 binding을 손으로 작성해야 하고, AI 설정·훅은 자동 연결되지 않는다. `checkCutover`는 호출자가 제시한 수치·목록을 신뢰하지 않으므로 항상 `ok: false`다. 이를 임의의 `true`나 가짜 0건으로 바꾸지 않는다.

네 대상의 `nativeSmoke`는 모두 `unverified`다. 로컬 설치 Codex 0.161.0에 대한 이전 역할 프로브는 실제 spawn 호출이 0회였고 모델 응답이 `agent_type` 부재를 주장한 것뿐이다. 따라서 사용자 정의 역할 실행 가능 여부는 **미검증**이지 Codex 전체에서 불가능하다고 판정한 사실이 아니다. API/CLI의 실제 스키마·도구 응답과 새 세션 관찰만 증거로 채택한다. Claude Code 실제 시험과 OpenCode·Antigravity 완료는 이번 야간 필수 범위에서 제외하고 미인증 상태로 남긴다.

화면 복원 `f3424b7`과 읽기 쉬운 가이드 `60c8c2e`는 준비된 별도 브랜치 작업이며 이 기준 브랜치에 아직 합쳐지지 않았다. 로케일 컴포넌트 수정 `551168e`는 독립 검토와 63/63 테스트를 통과했지만 통합 전이다. 화면의 일부 오류 문구 로케일은 1단계 후속 작업이다. 합친 후 실제 위젯/모듈을 연결한 DOM 검증과 전체 관련 테스트를 한 번 수행해야 한다.

## 접근 선택

1. **선택: 외부 범용 엔진 + 얇은 브리지.** 기존 엔진의 검증·runtime·대시보드와 도구별 후보 생성기를 활용하고, 프로젝트에는 식별 manifest와 도구가 실제 읽을 최소 네이티브 파일만 둔다. 소유권·롤백을 작은 경계에 묶을 수 있다.
2. 엔진 전체를 프로젝트마다 복사: 업데이트와 정책이 갈라지고 제품 checkout을 오염시키므로 제외한다.
3. runtime 격리만 하고 실제 도구 연결은 수동 유지: 화면은 뜨지만 첫 AI 작업과 에이전트 증거를 보장하지 못하므로 완료안이 아니다.

## 사용자가 보는 흐름

`npm run setup`을 새 대화형 진입점으로 제안한다. **현재 존재하는 명령이 아니다.** 먼저 `새 프로젝트`/`기존 프로젝트 연결`, 프로젝트 절대경로, 사용할 AI 도구를 묻는다. 기본 안내는 Codex 하나로 시작하되 도구 선택권을 보존한다. 입력 검증 후 변경 목록·소유 파일·충돌·백업·검증 가능/불가능 항목을 읽기 전용 계획으로 보여주고, 명시적인 Apply에서만 쓴다. 비대화형 사용은 같은 엔진 절차를 정확한 옵션과 승인 게이트로 호출할 수 있어야 한다. 많은 필수 플래그를 첫 화면에 노출하지 않는다.

새 프로젝트는 빈 경로 또는 안전하게 식별된 새 Git checkout만 받아 구조를 만들고, 식별 manifest·로컬 binding·최소 네이티브 브리지만 설치한다. 기존 프로젝트는 원본 파일의 존재·내용·소유권과 현재 훅/설정을 조사한 뒤 충돌이 없거나 명시적으로 검토된 파일만 추가·병합한다. 사용자 `AGENTS.md`, 사적 설정, `.ai/` 데이터, 기존 도구 설정을 덮어쓰거나 Harness 코어 전체를 복사하지 않는다. 중첩 루트·잘못된 ID·symlink 경계·오래된 binding·권한 부족은 쓰기 전에 중단하고 이유를 표시한다. `projects/<id>/`는 관리 데이터이며 제품 checkout이 아니다. 다중 프로젝트 스키마는 나중을 위한 선택 사항으로 남긴다.

도구 선택 뒤 후보 파일의 실제 네이티브 등록과 스킬 발견 위치를 확인한다. 도구가 외부 저장소의 파일을 직접 발견하지 못하면 프로젝트에 도구 네이티브 형식의 **버전·소유권이 기록된 생성 설정/역할/Skill 파일**이 필요할 수 있다. 이는 엔진 구현·runtime 복제가 아니며, 심볼릭 링크나 외부 경로 참조가 모든 도구에서 작동한다고 가정하지 않는다. 정적 생성 파일을 이용한 에이전트 사용은 소비자에서 Node 없이도 가능해야 한다. 다만 실시간 훅 기록과 대시보드는 Node 설치가 있을 때만 제공되는 별도 기능이다. 네 대상용 결정론적 생성 코드는 유지하되 이번 완료에서 실사용 증거의 필수 대상은 로컬 Codex다. 다른 세 대상은 후보/문서 상태만 정확히 표시하며 지원 완료로 홍보하지 않는다. 모델, 동시성, fork, 토큰 최적화, 글로벌 도구 설정, provider/auth를 설치 과정에서 변경하지 않는다. 선택 도구/버전에서 필요한 역할 호출이나 권한 경계가 확인되지 않으면 기능별 `미확인`을 표시하고 조용히 기본 역할로 대체하지 않는다.

## 안전한 적용·운영·업데이트

Apply는 계획의 대상 경로와 현재 해시를 재검증하고, 소유 파일을 백업·기록한 다음 원자적으로 쓰며 중간 실패 시 소유 범위만 복구한다. 외부 프로세스가 같은 파일을 바꾸면 자동 병합하지 않고 재검토를 요구한다. 설정 병합은 기존 키·주석·훅 순서/의미를 보존해야 한다. 로컬 binding/pointer의 변경은 이전 바이트를 보관하고 원자적 교체와 검증된 롤백을 제공한다. 시스템별 경로는 로컬 전용 파일에 두고 추적 대상에 넣지 않는다. `update`도 동일한 계획→검토→적용→검증 경로를 사용하며 원본 프로젝트 cleanup은 **범위 밖**이다. 기존 `.codex/`나 `.agents/`를 전부 지울 수 있다고 전제하지 않는다. 새 설치는 과거 runtime 이관이 아니다.

기존 runtime 전환은 별도 경계다. 먼저 기존 파일명·크기·해시, pointer 바이트, 실제 세션/작성자/claim 상태를 읽고 보존한다. 새 선택 프로젝트에서 명령·대시보드·역할·Skill·현재 계약의 다섯 훅을 해당 버전의 실제 지원 범위에서 검증한다. 신뢰 리더는 브리지가 직접 시작·관찰한 세션과 writer/claim의 정지 상태만 증명할 수 있으며, 외부 세션이나 생존 여부를 OS 전역에서 맹목적으로 인증할 수 없다. 관찰 범위 밖 세션이 있거나 상태를 알 수 없으면 legacy cutover는 차단한다. 호출자 입력 배열·숫자·문구는 증거가 아니다. 실패나 사후 검증 실패 시 새 세션을 멈추고 pointer 바이트를 되돌리며 두 runtime을 모두 보존한다. 실제 원본 전환·데이터 이관은 별도 리뷰/승인이 필요하다.

Lifecycle에는 실제 네이티브 인스턴스 ID를 시작·정지·재개·종료에 일치시킨다. 후속 턴은 같은 ID와 고유 turn token으로 조정하고, 훅과 orchestration 기록이 충돌하면 훅의 정확한 이벤트를 우선한다. 응답 없음이나 경과 시간만으로 생존, 성공, 종료를 추론하지 않는다. 런타임 실패는 사용자 작업을 취소하지 않되 화면에 기록 품질을 드러낸다. 토큰 화면은 선택 프로젝트의 실제 rollout만 명시적으로 가져오며, 소스가 없거나 일부만 관찰되거나 태스크 귀속이 불확실하면 `0` 대신 미확인/부분/귀속 불가를 표시한다. 프롬프트, 출력 본문, 자격 증명, 원본 로그 경로를 분석 저장소나 UI에 노출하지 않는다. 작업 선택 유지·새로고침 실패·오래된 표시 상태도 확인한다.

## 검증·통합 경계

구현은 엔진/브리지 격리 fixture에서 새 경로와 기존 경로의 읽기 전용 계획, 안전한 Apply, 충돌·중단·재시도·롤백을 먼저 검증한다. 읽기 전용 계획은 바이트 변경이 없어야 한다. 실제 지원되는 Codex 훅과 역할 호출은 설치 버전·모델·세션·권한·명령/도구 응답을 기록한 새 fixture 세션에서 관찰한다. `agent_type` 가능 여부도 실제 지원 스키마와 호출 결과로 판단한다. 기능별 관찰 실패는 원인을 표시하고 해당 항목을 미완료로 남긴다. 전환 게이트에는 가짜 입력이 통과하지 않는 회귀 테스트와 신뢰 리더 증거의 긍정/부정 fixture 테스트가 필요하다.

UI 브랜치와 가이드 브랜치를 합칠 때 다른 위젯을 가짜 마크업으로 대체하지 않는다. 실제 모듈을 연결한 DOM 테스트에서 탭 전환·내비게이션·토큰 새로고침 실패·차단된 private URL을 확인하고, 관련 전체 suite를 한 번 돌린다. Node가 선택적인 오프라인 갤러리도 열리는 경로로 확인한다. 실제 앱 링크는 실행·검증된 서버의 주소일 때만 보여준다. 안내문은 현재 가능한 수동 흐름과 미래 자동 진입점을 혼동하지 않으며, 구현 후에는 정확한 새/기존 시작 단계와 실패·복구 단계를 제시한다.

사용자가 요청한 밤샘 범위는 위 **완료 기준을 재계획하고 승인 뒤 순서대로 검증하는 것**이지 미확인 기능을 통과 처리하는 것이 아니다. YouTube/문서 내보내기/코드 분석/참고자료/오픈소스/태스크 iframe Skill 아이디어는 이후 별도 판단으로 미룬다. 외부 설치·글로벌 설정·인증·모델 선택 변경은 이번 범위에 없다. 검증 불가한 외부 기능은 명시적으로 미완료로 보고한다.

## 사용자 검토 선택 (최대 세 항목)

1. 소스 배치: 앞서 정한 비중첩 엔진 설치 + 별도 프로젝트 checkout을 권장 기본값으로 확정할지.
2. 실사용 완료선: 이번에는 로컬 Codex 네이티브 역할·Skill·훅 증거까지 필수로 하고 다른 세 대상은 `unverified`로 남길지.
3. 원본 정리: 기존 프로젝트 cleanup과 실제 legacy runtime 이관을 이번 완료에서 제외할지.

이 세 기본값은 지금까지의 방향과 맞지만 이 문서 자체가 구현 승인이나 진짜 cutover 승인은 아니다. 검토·승인 뒤 구현 계획을 작성한다.
