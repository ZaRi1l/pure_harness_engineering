# Project-Scoped Token Telemetry MVP Design

## Purpose and success

Show what token usage is actually observable for one selected Pure Harness project without retaining conversation content or presenting unknown usage as zero. The Dashboard should distinguish measured totals from missing, partial, and unsupported sources; allow an all-tasks snapshot or one selected task; show exact role/agent attribution when evidence exists; and expose the unattributed remainder. This is neutral workflow telemetry, not a product analytics or billing system.

## Chosen approach and alternatives

Add an optional, versioned normalized aggregate to each validated project's managed runtime and a read-only Dashboard panel. Producers submit normalized aggregate data; the first adapter is an explicit-path Codex rollout JSONL importer invoked by the operator. No background scan, global rollout discovery, shared cross-project database, or source-log copy is used. A raw-log viewer would violate the privacy goal; inferring task assignment from timestamps, titles, or proximity would make attractive but false breakdowns. Importing replaces the project's prior telemetry snapshot rather than accumulating it, so rerunning the same input cannot double-count it.

## Components and data flow

- A neutral normalization boundary accepts only an allowlisted aggregate: `schema_version`, `project_id`, `observed_at`, source/status, start/end timestamps, elapsed milliseconds, totals, task breakdown, role/agent breakdown, unattributed total and fraction, Largest Tool Outputs, spawn distribution, compactions, and coverage counts. Token metrics are `input`, `output`, `processed = input + output`, `cached_input` (a subset of input), and `reasoning_output` (a subset of output); subsets are never added again to processed. Optional metrics include response count and tool calls. Counts are nonnegative safe integers or `null`; unknown, unsupported, or incomplete metrics stay `null`, never zero. A measured empty interval may be zero with observed status. Elapsed time is end minus start only when both valid timestamps are observed, never a wall-clock guess. Unsupported optional fields are omitted rather than fabricated.
- The importer is CLI-only and requires one or more explicit JSONL file paths plus the validated selected-project context. It streams records and derives only aggregate numbers and exact IDs. For supported per-response usage records, it keys by `(thread_id, response_id)` and counts one record once; identical repeats are ignored and conflicting repeats invalidate that thread's token coverage. A per-response set is complete only when the supported source format establishes that every response has a recognized usage record and none is invalid. It does not sum cumulative usage snapshots: for a thread with supported cumulative counters, it takes the last snapshot in source order only after checking that counters are monotonic and the thread identity is stable. If per-response and cumulative records coexist, the validated final cumulative counters are the thread total and per-response records may support attribution only; they are never added to that total. Without a supported complete per-response set or valid final cumulative snapshot, affected metrics are `null` and coverage is partial/unsupported. Cached and reasoning subset bounds are validated. Source paths are never placed in the normalized document, runtime events, HTTP responses, or error details exposed by the Dashboard.
- Attribution uses only exact native thread/turn/root-turn/child-agent/task identifiers from source records joined to explicit identifiers in the selected project's runtime. The current runtime records agent ID and optional `task_id`; it does not yet guarantee root-turn linkage, so a root-turn join is used only if explicit linkage is available, never invented. A segment is assigned to a task only when that join is unique and complete; otherwise its measured tokens stay in the project total and, when calculable, the unattributed remainder. Role and agent rows carry only exact child ID, parent ID, role, task ID, and `fork_turns` values when observed; unknown parentage or ambiguous links remain null. A spawn distribution counts observed attempts and confirmed child spawns separately by parent, child, role, task, and `fork_turns`; no inferred spawn is shown. No free-text matching, timestamp-window guesses, or cross-project lookup is allowed.
- Largest Tool Outputs groups confirmed tool-call outputs by normalized tool name and displays call count, total UTF-8 output bytes, median, p95, and maximum bytes, sorted by total bytes descending. Median uses the midpoint (mean of the middle pair for even counts); p95 uses the nearest-rank observation. Output bodies are discarded after measuring bytes. Compaction counts include only explicit observed compaction events; unsupported coverage is unknown rather than zero.
- The store validates `project_id`, schema, numeric ranges, and the allowlist, then atomically replaces the selected project's telemetry document under its runtime lock. `GET /runtime/telemetry` returns that safe document or an explicit missing state. The existing snapshot may include the same normalized aggregate for the live Dashboard, but no raw importer records. The Dashboard offers Task Snapshot: All tasks (project aggregate) and exact task-ID selection. It shows coverage/status, token totals, role/agent rows, Largest Tool Outputs, spawn distribution, observed compactions, start/end/elapsed, and unattributed tokens and fraction only when both numerator and denominator are known and denominator is positive. A selected task shows only exactly attributable metrics and states the unassigned portion is excluded. A partial total is labeled partial; incompatible or unavailable metrics display “Unknown,” never `0` or a computed rate.

## Error, privacy, and isolation boundaries

Malformed JSONL fails the entire import atomically with a line-number diagnostic that excludes line contents and source path from persisted state. Unknown non-usage record types in a recognized source version are ignored; an unrecognized source version or unknown usage-bearing shape is marked unsupported for that thread, without guessing field meanings. Invalid counters, conflicting duplicate response IDs, counter resets, or mixed/ambiguous thread identity mark affected token metrics unknown/partial; a structural error that prevents safe thread isolation aborts the import without replacing the last good aggregate. A valid input with no usable usage records yields missing/unsupported coverage, not a false zero. Empty and unavailable states are explicit in the UI. Read failures leave the previous displayed value marked stale until a successful refresh.

Persist an explicit allowlist only. Never persist prompts, messages, tool arguments, tool output bodies, raw records, source paths, filesystem paths, or arbitrary model-provided labels. Tool names and model/role identifiers are normalized to bounded known values or `other`/null; no source filename appears in a UI label. Do not log record contents on errors. The importer and read route use only the validated selected project's runtime; a document stamped for another project is rejected. Telemetry reads use the existing localhost/no-store server boundary, and no browser upload or write endpoint is introduced.

## Verification and non-goals

Fixture tests cover observed, missing, partial, and unsupported usage; per-response deduplication and conflicting duplicates; cumulative snapshots without re-summing, mixed modes, and reset/unknown cases; processed/subset equations; multiple turns; unique, ambiguous, and absent attribution; null propagation and zero only when measured; all-tasks versus selected-task snapshots; role/agent and spawn breakdown; unattributed arithmetic; UTF-8 tool bytes and median/p95/max; observed compactions and start/end/elapsed; malformed-line atomic failure and source-version uncertainty; and import replacement/idempotence. Privacy tests assert the persisted JSON, HTTP payload, and events contain no sentinel prompt/body/path text. Two-project fixtures verify isolation and identity rejection. Focused importer/store/server/dashboard tests precede `npm test` and `npm run self-check`. Automated DOM/HTTP checks establish data behavior only; actual browser presentation is for human validation.

Non-goals: cost or price estimates, billing-grade accounting, quota prediction, time-series history, automatic filesystem discovery, live provider API collection, cross-project comparison, content inspection, user-level tracking, or product-specific telemetry.
