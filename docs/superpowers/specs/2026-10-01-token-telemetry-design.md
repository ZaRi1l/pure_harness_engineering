# Project-Scoped Token Telemetry MVP Design

## Purpose and success

Show what token usage is actually observable for one selected Pure Harness project without retaining conversation content or presenting unknown usage as zero. The Dashboard should distinguish measured totals from missing, partial, and unsupported sources, show exact task/agent attribution when evidence exists, and expose the unattributed remainder. This is neutral workflow telemetry, not a product analytics or billing system.

## Chosen approach and alternatives

Add an optional, versioned normalized aggregate to each validated project's managed runtime and a read-only Dashboard panel. Producers submit normalized aggregate data; the first adapter is an explicit-path Codex rollout JSONL importer invoked by the operator. No background scan, global rollout discovery, shared cross-project database, or source-log copy is used. A raw-log viewer would violate the privacy goal; inferring task assignment from timestamps, titles, or proximity would make attractive but false breakdowns. Importing replaces the project's prior telemetry snapshot rather than accumulating it, so rerunning the same input cannot double-count it.

## Components and data flow

- A neutral normalization boundary accepts only an allowlisted aggregate: `schema_version`, `project_id`, `observed_at`, source/status, totals, task breakdown, agent breakdown, unattributed total, tool-name/count/byte-size breakdown, and coverage counts. Token metrics include input, output, processed, cached input, and reasoning output. Optional aggregate metrics include response count, tool calls/output-byte distributions, spawn attempts/successes, fork-turn counts, compactions, and elapsed time. Counts are nonnegative safe integers or `null`; unknown, unsupported, or incomplete metrics stay `null`, never zero. A measured empty interval may be zero with observed status. Unsupported optional fields are omitted rather than fabricated.
- The importer is CLI-only and requires one or more explicit JSONL file paths plus the validated selected-project context. It streams records, deduplicates identical usage by exact response ID within the import set, and derives only aggregate numbers and IDs. It calculates tool output byte lengths in memory, not output text. It rejects malformed files or conflicting duplicate/ambiguous exact IDs that could double-count, and writes nothing until the full import validates. Source paths are never placed in the normalized document, runtime events, HTTP responses, or error details exposed by the Dashboard.
- Attribution uses only exact native thread/turn/root-turn/child-agent/task identifiers from source records joined to explicit identifiers in the selected project's runtime. The current runtime records agent ID and optional `task_id`; it does not yet guarantee root-turn linkage, so a root-turn join is used only if explicit linkage is available, never invented. A segment is assigned to a task only when that join is unique and complete; otherwise its measured tokens stay in the project total and, when calculable, the unattributed remainder. Agent breakdown is likewise limited to exact child-agent IDs. Unknown parentage or ambiguous links remain null. No free-text matching, timestamp-window guesses, or cross-project lookup is allowed.
- The store validates `project_id`, schema, numeric ranges, and the allowlist, then atomically replaces the selected project's telemetry document under its runtime lock. `GET /runtime/telemetry` returns that safe document or an explicit missing state. The existing snapshot may include the same normalized aggregate for the live Dashboard, but no raw importer records. The Dashboard shows status/coverage, total tokens, exact task and agent rows, and unattributed tokens/percent only when both numerator and denominator are known. A partial total is labeled partial; incompatible or unavailable metrics display “Unknown,” never `0` or a computed rate.

## Error, privacy, and isolation boundaries

Malformed JSONL, unsupported record shapes, invalid counters, or mixed/ambiguous identity fail the import with no replacement of the last good aggregate. A valid input with no usable usage records yields missing/unsupported coverage, not a false zero. Empty and unavailable states are explicit in the UI. Read failures leave the previous displayed value marked stale until a successful refresh.

Persist an explicit allowlist only. Never persist prompts, messages, tool arguments, tool output bodies, raw records, source paths, filesystem paths, or arbitrary model-provided labels. Tool names and model/role identifiers are normalized to bounded known values or `other`/null; no source filename appears in a UI label. Do not log record contents on errors. The importer and read route use only the validated selected project's runtime; a document stamped for another project is rejected. Telemetry reads use the existing localhost/no-store server boundary, and no browser upload or write endpoint is introduced.

## Verification and non-goals

Fixture tests cover observed, missing, partial, and unsupported usage; exact deduplication; multiple turns; unique, ambiguous, and absent attribution; null propagation; zero only when measured; unattributed arithmetic; tool byte aggregation; malformed/oversized input handling; and import replacement/idempotence. Privacy tests assert the persisted JSON, HTTP payload, and events contain no sentinel prompt/body/path text. Two-project fixtures verify isolation and identity rejection. Focused importer/store/server/dashboard tests precede `npm test` and `npm run self-check`. Automated DOM/HTTP checks establish data behavior only; actual browser presentation is for human validation.

Non-goals: cost or price estimates, billing-grade accounting, quota prediction, time-series history, automatic filesystem discovery, live provider API collection, cross-project comparison, content inspection, user-level tracking, or product-specific telemetry.
