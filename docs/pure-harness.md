# Pure Harness fixed-project runtime

The supported installation has one independent Git checkout at `project/` and ignored local state under `.harness/`. Start with [the short setup guide](../README.md#처음-시작하기): run interactive `npm run setup`, review and confirm its plan, then run `npm run init` once. Open `project/` in the AI tool. From the Harness root, `npm run status` and `npm run preview:live` are the ordinary commands; neither takes a project selector. `npm run self-check` checks the engine and configured fixed project without old binding arguments. File placement and CLI checks do not establish native role, Skill, or hook execution.

`scripts/project-diagnostic.mjs`, `inspectProjectBinding`, and the optional `projectBinding` input to `checkRepository` remain read-only historical binding interfaces for legacy fixtures or explicit diagnostics. They do not select the normal installation, initialize its runtime, migrate an older project, or certify a native tool. Do not use their former multi-project command sequence as a setup procedure. The fixed-project setup plan and its conflict checks are the supported path.

For engine-source maintenance only, run `node scripts/runtime-state.mjs --core claim <agent-id> <engine-relative-path> [...]` and later `node scripts/runtime-state.mjs --core release-claim <agent-id>`. This uses the separate core runtime and rejects product-managed paths. Product claims use the configured fixed project, for example `node scripts/runtime-state.mjs claim <agent-id> <project-relative-path>` after setup; do not mix product and `--core` claims.

The live guide is the server-printed localhost URL with `#guide`, not direct `file://` access to `preview/index.html`. The separate [offline gallery](../offline-gallery/index.html) and its [standalone sketch](../offline-gallery/tasks/example.html) can be opened as local files but do not show live project runtime.
